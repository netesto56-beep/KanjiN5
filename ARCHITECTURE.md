# ARCHITECTURE.md — Kanji N5
Документ описывает устройство приложения после подключения **Supabase**.
Главное изменение по сравнению с первой версией: приложение больше не хранит
прогресс в `localStorage`. Вход выполняется через **Supabase Auth**, данные лежат
в таблицах **`users`**, **`kanji`** и **`user_progress`**, а доступ между
пользователями разграничивает **RLS (Row Level Security)** на стороне Postgres.
---

Сборка статическая (`dist/`), отдельного бэкенда у приложения нет — его роль
полностью выполняет Supabase.

## 2. Аутентификация: Supabase Auth
Единственный способ получить доступ к прогрессу — войти по email и паролю.
Свой сервер логина не используется.
| Операция | Метод `SupabaseAuthService` | Что вызывает в SDK |
|---|---|---|
| Текущий пользователь | `getCurrentUser()` | `auth.getSession()` (без сети) |
| Вход | `signIn(email, password)` | `auth.signInWithPassword` |
| Регистрация | `signUp(email, password)` | `auth.signUp` |
| Выход | `signOut()` | `auth.signOut` |
| Реакция на вход/выход | `onAuthStateChange(cb)` | `auth.onAuthStateChange` |
Ключевые решения:
- **Один клиент на всё приложение.** `supabase/client.js` создаёт клиент с
  `persistSession`, `autoRefreshToken`, `detectSessionInUrl`. Поэтому токен
  хранится в `localStorage` браузера и автоматически обновляется.
- **Сессия — источник истины.** `onAuthStateChange` присылает `INITIAL_SESSION`
  при загрузке страницы, поэтому отдельного опроса «залогинен ли» нет.
  Повторные события для того же пользователя (`TOKEN_REFRESHED`) не перезагружают
  данные — в `app.js` это защищено проверкой `nextId === currentUserId`.
- **Гонки при смене пользователя.** Каждое событие авторизации увеличивает
  `authGeneration`; асинхронные загрузки сверяют поколение и не применяют чужой
  ответ (быстрый выход → вход другим аккаунтом).
- **Пока сессии нет**, интерфейс показывает модальное окно входа, а карточка
  остаётся видимой (без прогресса). Нажатие оценки без входа снова открывает
  окно входа, а не пишет в облако.
- **Подтверждение email** настраивается в Supabase. `signUp` возвращает
  `needsEmailConfirmation = true`, если сессии ещё нет, и UI просит перейти по
  ссылке из письма.
- **Ошибки Supabase переводятся** на русский (`translateAuthError`): неверный
  пароль, неподтверждённый email, занятый email, короткий пароль, rate limit,
  отсутствие сети.
У пользователя в приложении есть только `id`, `email`, `isAnonymous` — поля
`auth.users` наружу не отдаются.

## 3. Модель данных
### 3.1. `auth.users` (системная, Supabase Auth)
Хранит учётные записи, хэши паролей, подтверждение email, выдаёт JWT.
Приложение читает её только через Auth API, напрямую в SQL не обращается.
### 3.2. `public.users` — профиль
| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `UUID PK` | Тот же id, что `auth.users.id` (`REFERENCES auth.users(id) ON DELETE CASCADE`) |
| `email` | `TEXT` | Дублируется для удобства чтения и отображения |
| `is_anonymous` | `BOOLEAN NOT NULL DEFAULT FALSE` | Признак анонимного входа |
| `created_at` | `TIMESTAMPTZ` | Дата создания |
Строка создаётся **триггером** `on_auth_user_created` → `public.handle_new_user()`
(`SECURITY DEFINER`, `INSERT ... ON CONFLICT DO NOTHING`), то есть сразу при
регистрации. Для аккаунтов, созданных до установки триггера, клиент вызывает
`progressRepo.ensureProfile(user)` перед записью прогресса.
### 3.3. `public.kanji` — справочник (общий, только чтение)
| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `SERIAL PK` | Числовой идентификатор |
| `kanji` | `VARCHAR(10) UNIQUE` | Сам иероглиф |
| `meaning` | `TEXT` | Перевод |
| `onyomi`, `kunyomi` | `JSONB` (массивы) | Чтения |
| `examples` | `JSONB` (массив объектов `word`, `reading`, `meaning`) | Примеры слов |
| `created_at` | `TIMESTAMPTZ` | — |
Индекс `idx_kanji_character`. Данные заливаются из `kanji.json` скриптом
`supabase_seed_kanji.sql` (генератор — `pnpm seed:sql`).
### 3.4. `public.user_progress` — прогресс
| Колонка | Тип | Смысл |
|---|---|---|
| `user_id` | `UUID` → `users(id) ON DELETE CASCADE` | Владелец строки |
| `kanji_id` | `INTEGER` → `kanji(id) ON DELETE CASCADE` | Кандзи |
| `rating` | `TEXT CHECK (rating IN ('unknown','hard','easy','known'))` | Отметка |
| `updated_at` | `TIMESTAMPTZ DEFAULT NOW()` | Время последнего изменения |
Первичный ключ — `(user_id, kanji_id)`, поэтому на одну пару «пользователь +
кандзи» всегда ровно одна строка. Сохранение — `upsert` с
`onConflict: 'user_id,kanji_id'`. Индексы: `idx_user_progress_user`,
`idx_user_progress_rating`.
### 3.5. Связи
```
auth.users 1 ──── 1 public.users
                        │ 1
                        │
                        │ N
                public.user_progress N ──── 1 public.kanji
```
Важно: в приложении прогресс — это объект `{ [кандзи]: rating }`, а в БД —
строки с числовым `kanji_id`. Преобразование туда и обратно делает
`repositories/progress.repository.js` (ленивая карта `id ↔ kanji` из таблицы
`kanji`, кэшируется в памяти на время сессии).

## 4. RLS: защита данных
Доступ к строкам разграничивается **на сервере** политиками Row Level Security,
а не кодом интерфейса. Клиент физически не может прочитать чужой прогресс, даже
если вручную подставит чужой `user_id` в запрос.
### 4.1. Включение и политики
```sql
alter table public.users         enable row level security;
alter table public.kanji         enable row level security;
alter table public.user_progress enable row level security;
```
| Таблица | Политика | Правило |
|---|---|---|
| `users` | select | `auth.uid() = id` |
| `users` | insert | `with check (auth.uid() = id)` |
| `users` | update | `using (auth.uid() = id)` |
| `kanji` | select | `true` (справочник читают все, в т.ч. `anon`) |
| `user_progress` | select | `auth.uid() = user_id` |
| `user_progress` | insert | `with check (auth.uid() = user_id)` |
| `user_progress` | update | `using (auth.uid() = user_id)` |
| `user_progress` | delete | `using (auth.uid() = user_id)` |
Политик на запись в `kanji` нет: кандзи меняются только через SQL Editor /
сид-скрипт, из приложения они read-only.
### 4.2. Что дополняет RLS
- **`GRANT`-права.** RLS фильтрует строки, но не выдаёт доступ к таблице. Сид
  выдаёт `select` на `kanji` ролям `anon` и `authenticated`,
  `select/insert/update` на `users` и полный набор на `user_progress` — только
  роли `authenticated`.
- **`SECURITY DEFINER` у триггера.** Вставка профиля в `public.users` происходит
  от имени владельца функции и обходит RLS, иначе регистрация упиралась бы в
  политику `insert`, где `auth.uid()` ещё не совпадает с новой строкой.
- **`auth.uid()` вместо параметра из URL.** Политика не доверяет телу запроса:
  она сравнивает колонку с id из проверенного JWT.
- **В клиенте нет `service_role` ключа.** Используется только anon/publishable
  key — он публичен по определению, и именно RLS делает его безопасным.
- **Каскады.** `ON DELETE CASCADE` от `auth.users` гарантирует, что удаление
  пользователя удаляет и профиль, и весь его прогресс.
- **Проверка `rating`** на уровне `CHECK` — в БД нельзя записать значение вне
  четырёх допустимых.
### 4.3. Как это проверяется
- `pnpm check:supabase` — URL, ключ, доступность таблиц.
- `pnpm check:rls` — прямое обращение к API от имени пользователя B с
  `user_id` пользователя A; ожидается пустой результат и запрет записи.
- `RLS_TESTING.md` — пошаговый чек-лист двумя аккаунтами (браузер + прямой API).
Важно: проверка «двумя вкладками» сама по себе RLS не доказывает — клиент и так
запрашивает только свои строки. Изоляцию обеспечивает сервер, поэтому второй
уровень (прямой запрос) обязателен.

## 5. Слои и модули
```
app.js                    состояние, DOM, синхронизация, обработка ошибок
├── domain/               чистые функции без сети и DOM
│   ├── card-selector.js  выбор следующей карточки с учётом фильтра
│   └── progress-summary.js подсчёт и форматирование сводки
├── repositories/         доступ к данным (интерфейс + реализация Supabase)
│   ├── kanji.repository.js    таблица kanji, откат на kanji.json
│   └── progress.repository.js таблица user_progress, upsert, профиль
├── auth/auth.service.js  Supabase Auth, подписка, тексты ошибок
├── lib/offline-store.js  кэш прогресса и очередь повтора в localStorage
└── supabase/client.js    единый клиент и чтение конфигурации
```
Правила, которых придерживается код:
1. **`domain/` ничего не знает о Supabase.** Функции принимают данные и
   возвращают данные, поэтому их можно тестировать без браузера и сети.
2. **`app.js` не пишет SQL-подобные запросы.** Всё общение с БД — через
   репозитории, у каждого есть фабрика (`create*Repository`) для подмены в тестах.
3. **Сеть не управляет интерфейсом напрямую.** Ошибка запроса превращается в
   статус синхронизации и запись в очередь, а не в откат экрана.

## 6. Потоки данных
### 6.1. Старт приложения
1. Проверяется конфигурация (`isSupabaseConfigured`). Без URL/ключа — фатальный
   экран, а не «пустое приложение».
2. Загружается справочник кандзи: сначала `kanji`, при пустоте или ошибке —
   `kanji.json`.
3. Создаются репозитории и сервис авторизации.
4. Карточка рендерится сразу, параллельно открывается окно входа и запрашивается
   текущая сессия (`onAuthStateChange` + страховочный `getCurrentUser`).
### 6.2. Вход
`signIn` → JWT в `localStorage` → событие Auth → `handleAuthChange` →
`loadForUser`:
1. Читается очередь несохранённого (`readPending`) и локальный кэш
   (`readProgressCache`).
2. Запрашивается облако: `select kanji_id, rating from user_progress where user_id = …`.
3. Слияние по приоритету: **очередь → облако → локальный кэш**.
4. Кэш перезаписывается, сводка и карточка обновляются, очередь (если есть)
   отправляется.
### 6.3. Оценка карточки
```
нажатие кнопки
  → progress[kanji] = rating (оптимистично, сразу в UI)
  → запись в локальный кэш
  → upsert в user_progress
      ├── успех  → статус «Сохранено в облаке», очередь чистится
      └── ошибка → rating в очередь повтора, статус «Повторим позже»
```
Оценка **никогда не откатывается** из-за сетевой ошибки: пользователь видит
свой выбор, внизу — честный статус синхронизации.
### 6.4. Повторная отправка
Очередь отправляется:
- следующим успешным сохранением (`scheduleFlush`);
- событием `online`;
- возвращением на вкладку (`visibilitychange`);
- таймером (`scheduleRetry`, 15 с).
Перед удалением записи из очереди проверяется, что отметка не изменилась
(`pending[kanji] === rating`), иначе более новая оценка была бы потеряна.
Флаг `flushInFlight` не даёт отправить очередь дважды параллельно;
`userId !== currentUserId` обрывает отправку при смене аккаунта.

## 7. Отказоустойчивость
Supabase — основное хранилище, но приложение остаётся работоспособным без него:
| Что | Приоритет источника | Что происходит при сбое |
|---|---|---|
| Справочник кандзи | `kanji` → `kanji.json` | Используется локальный JSON |
| Прогресс | очередь → облако → кэш | Показываются локальные данные, изменения в очередь |
| Аутентификация | сессия в `localStorage` | Окно входа, карточки без прогресса |
`lib/offline-store.js` — **страховка, а не второе хранилище**: все операции
обёрнуты в `try/catch`, потому что `localStorage` может быть недоступен
(приватный режим, переполнение) и не должен ломать приложение. Очередь хранит
только последнюю несохранённую отметку по каждому кандзи — это не журнал.

## 8. Конфигурация
`.env` (или `.env.local`) в корне проекта; Vite пробрасывает оба набора имён
(`envPrefix: ['VITE_', 'NEXT_PUBLIC_']`):
```env
NEXT_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon или publishable key>
```
Альтернативы: `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`,
`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, а также
`window.__SUPABASE_CONFIG__ = { url, anonKey }` для статической сборки.
Ключ `service_role` в клиент не попадает никогда.
Порядок настройки проекта: `supabase_schema_fixed.sql` (таблицы, RLS, триггер) →
`supabase_seed_kanji.sql` (данные + `GRANT`) → пользователи через
**Authentication → Users** или форму регистрации.

## 10. Ограничения и направления развития
- **Регистрация только email + пароль.** OAuth-провайдеры и magic link не
  подключены, хотя Auth их поддерживает.
- **Нет пагинации.** Справочник N5 (≈100 кандзи) грузится целиком и кэшируется
  в памяти; для больших наборов понадобится выборка по `id`.
- **Кэш прогресса — полная карта.** Для сотен кандзи это приемлемо, при росте
  объёма стоит перейти на инкрементальные выборки по `updated_at`.
- **Нет realtime-подписки.** Изменения с другого устройства подтянутся после
  перезагрузки или повторного входа; `supabase.channel` можно добавить точечно.
- **`ensureProfile` — обходной путь** для аккаунтов старше триггера; при чистой
  базе он не нужен.
