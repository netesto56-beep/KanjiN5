# Проверка изоляции данных (RLS) двумя аккаунтами

Документ описывает, как убедиться, что пользователь A не видит и не может изменить
прогресс пользователя B. Проверка делается в два уровня — это важно, см. ниже.

> **Быстрый прогон (≈10 минут):**
> 1. Создайте в Supabase двух пользователей с галочкой **Auto Confirm User**
>    (`kanji-test-a@…`, `kanji-test-b@…`).
> 2. Пропишите их в `.env` как `RLS_USER_A_EMAIL/PASSWORD` и `RLS_USER_B_…`.
> 3. `pnpm check:rls` → все строки должны быть `OK`.
> 4. Откройте `pnpm dev`, войдите как A в обычном окне и как B — в инкогнито.
> 5. A ставит отметки, B видит `Не знаю: 36`; затем наоборот.
> 6. Сверьтесь с чек-листом в конце документа.

---

## 0. Почему проверок два уровня

Приложение **само** подставляет `user_id` в запросы:

- `repositories/progress.repository.js` → `.eq('user_id', userId)` при чтении,
  `user_id: userId` при upsert;
- `app.js` → `progressRepo.get(user.id)` / `updateOne(userId, ...)`, где `userId`
  берётся из текущей сессии.

Поэтому если RLS **выключен**, браузерная проверка ничего не покажет: клиент и так
запрашивает только своё. Изоляцию обеспечивает **сервер**, а не интерфейс.

| Уровень | Что доказывает | Как проверять |
|---|---|---|
| 1. Браузер, два аккаунта | Продукт ведёт себя правильно: чужой прогресс не появляется в UI | Шаги 3–6 |
| 2. Прямой запрос к API от имени B с `user_id` A | RLS реально включён и блокирует чужие строки | Шаги 7–8 |

Уровень 2 — обязательный. Уровень 1 без уровня 2 ничего не гарантирует.

## 1. Шаг 1. Два тестовых аккаунта

В проекте включено подтверждение email (`mailer_autoconfirm: false`), поэтому
регистрация через форму требует перехода по ссылке из письма. Для теста проще
создать аккаунты сразу подтверждёнными:

1. Supabase Dashboard → **Authentication → Users → Add user → Create new user**.
2. Email: `kanji-test-a@example.com`, пароль от 6 символов,
   галочка **Auto Confirm User** — включена.
3. Повторите для `kanji-test-b@example.com`.

Пароли и email запишите — они понадобятся в шаге 7.

> Альтернатива: зарегистрировать оба аккаунта через форму приложения и подтвердить
> письма. Тогда в `Authentication → Users` у обоих должен быть статус Confirmed,
> иначе вход вернёт «Email не подтверждён».

Также проверьте, что у обоих пользователей появились строки в `public.users`
(их создаёт триггер `on_auth_user_created`): Table Editor → `users` → 2 строки.

## 2. Шаг 2. Две независимые сессии в браузере

Supabase хранит сессию в `localStorage` (ключ `sb-<ref>-auth-token`), а он общий
для всех вкладок одного профиля. Две вкладки в обычном окне — это **один**
пользователь, и выход в одной вкладке разлогинит другую.

Поэтому откройте две независимые сессии любым способом:

- обычное окно + окно в режиме инкогнито (проще всего), **или**
- два разных браузера, **или**
- два профиля Chrome (`chrome://profile-picker`).

Затем в каждом:

```bash
pnpm dev          # http://127.0.0.1:5173
```

- Окно 1 → вход как **A** (`kanji-test-a@example.com`).
- Окно 2 → вход как **B** (`kanji-test-b@example.com`).

Убедитесь, что в панели сверху в каждом окне показан **свой** email.

> Не запускайте два dev-сервера на разных портах «чтобы разделить сессии»:
> ключ localStorage привязан к origin, и `127.0.0.1:5173` vs `localhost:5173` —
> это разные origin, но это лишнее усложнение. Инкогнито достаточно.

## 3. Шаг 3. A ставит отметки

В окне A, на свежем аккаунте сводка должна быть:

```
Не знаю: 36 | Трудно: 0 | Легко: 0 | Знаю: 0
```

(36 — число кандзи в `kanji.json`; сумма четырёх чисел всегда равна 36.)

Поставьте три отметки на конкретных карточках и запомните, какие:

| Кандзи | Отметка |
|---|---|
| 学 | Знаю |
| 日 | Трудно |
| 月 | Легко |

Ожидаемо: сводка стала `Не знаю: 33 | Трудно: 1 | Легко: 1 | Знаю: 1`,
внизу статус «Прогресс сохранён в облаке».

## 4. Шаг 4. B не видит прогресс A

Важно: сначала **обновите окно B (F5)**. Иначе B покажет данные, загруженные при
входе, и проверка ничего не докажет — нужно, чтобы клиент заново запросил прогресс
у сервера.

После F5 в окне B (свежий аккаунт) проверьте:

- [ ] сводка всё ещё `Не знаю: 36 | Трудно: 0 | Легко: 0 | Знаю: 0`;
- [ ] фильтр «Знаю» у B пуст (если бы B видел отметки A, там был бы 学);
- [ ] в панели сверху email B.

Затем в окне B поставьте свою отметку: 学 → **Легко**.

---

## 5. Шаг 5. Обратный ход: A не видит B

Вернитесь в окно A:

- [ ] нажмите F5 (перезагрузка) — данные перечитываются из облака;
- [ ] сводка A прежняя: `Не знаю: 33 | Трудно: 1 | Легко: 1 | Знаю: 1`
      (а не 2 «Легко»);
- [ ] отметка 学 у A осталась **Знаю**, хотя B поставил **Легко**.

Это ключевая проверка: одна и та же карточка `kanji_id` хранится в двух строках
`user_progress` с разными `user_id` и разными `rating`.

## 6. Шаг 6. Перекрёстная проверка в Table Editor

Supabase Dashboard → **Table Editor → user_progress**:

- [ ] есть строки с `user_id` A (3 шт.) и с `user_id` B (1 шт.);
- [ ] для `kanji_id` карточки 学 — две строки: у A `known`, у B `easy`.

Если фильтровать по `user_id`, чужих строк быть не должно. Чтобы увидеть email
рядом с UUID, откройте **SQL Editor** и выполните:

```sql
select p.user_id, u.email, p.kanji_id, k.kanji, p.rating, p.updated_at
from public.user_progress p
join public.users u on u.id = p.user_id
join public.kanji k on k.id = p.kanji_id
order by u.email, p.kanji_id;
```

## 7. Шаг 7. Автоматическая проверка RLS (главный шаг)

В репозитории есть готовый скрипт `scripts/check-rls.mjs`: он входит обоими
аккаунтами и **от имени B** пытается читать, вставлять, обновлять и удалять
строки **A**.

Добавьте в `.env` (файл в `.gitignore`, в репозиторий не попадёт):

```env
RLS_USER_A_EMAIL=kanji-test-a@example.com
RLS_USER_A_PASSWORD=ваш-пароль-A
RLS_USER_B_EMAIL=kanji-test-b@example.com
RLS_USER_B_PASSWORD=ваш-пароль-B
```

Запустите:

```bash
pnpm check:rls
```

Ожидаемый вывод — все строки `OK` (сокращённо):

```
=== Гость (без входа) ===
OK   гость не читает user_progress — 42501: permission denied for table user_progress
OK   гость не пишет в user_progress — 42501: permission denied for table user_progress
OK   гость не читает профили users — 42501: permission denied for table users
OK   гость читает kanji (так и задумано) — 3 строк

=== Вход тестовыми аккаунтами ===
A: kanji-test-a@example.com — 1111…
B: kanji-test-b@example.com — 2222…

=== Подготовка данных ===
OK   A создаёт/обновляет свой профиль
OK   A сохраняет свою отметку «easy»

=== B пытается читать данные A ===
OK   A видит свою отметку — easy
OK   B без фильтра получает только свои строки — своих 1, чужих 0
OK   B не видит строки A по явному запросу user_id=A — 0 строк
OK   B не видит профиль A — 0 строк

=== B пытается менять данные A ===
OK   B не может вставить строку с user_id=A — 42501: new row violates row-level security policy ...
OK   B не может обновить строки A — обновлено 0
OK   отметка A не изменилась — easy
OK   B не может удалить строки A — удалено 0
OK   строка A уцелела после удаления — easy
OK   B не может обновить профиль A — обновлено 0
OK   B не может вставить профиль с id=A — 42501: ...
OK   профиль A не испорчен — kanji-test-a@example.com

=== B пишет своё, A не должен это увидеть ===
OK   B сохраняет свою отметку
OK   A не видит строки B — 0 строк

Чистка: отметка A для 学 возвращена в исходное состояние

```

Скрипт сам возвращает отметку A на тестовом кандзи в исходное состояние и
завершается с кодом `1`, если хоть одна проверка провалилась.

Быстрая проверка без аккаунтов (только гость):

```bash
pnpm check:rls -- --anon-only
```

> Уже выполнено на вашем проекте: все 4 гостевые проверки — OK. Гость получает
> `42501 permission denied` на `user_progress` и `users` и читает только `kanji`.

## 8. Шаг 8. Ручная проверка через REST (по желанию)

Чтобы увидеть то же самое своими глазами. Возьмите токен B: DevTools →
**Application → Local Storage → `http://127.0.0.1:5173`** → ключ
`sb-<ref>-auth-token` → поле `access_token` (длинная строка `eyJ…`).

В PowerShell (значения `$url` и `$key` — из `.env`, `$A_ID` — UUID аккаунта A
из Authentication → Users):

```powershell
$url  = "https://<ref>.supabase.co"
$key  = "<publishable key из .env>"
$tokenB = "<access_token аккаунта B>"
$A_ID = "<uuid аккаунта A>"
$h = @{ apikey = $key; Authorization = "Bearer $tokenB" }

# 1) Чужой прогресс. Ожидаем пустой массив []
Invoke-RestMethod "$url/rest/v1/user_progress?select=*&user_id=eq.$A_ID" -Headers $h

# 2) Запись от имени A. Ожидаем HTTP 401/403 с "row-level security"
Invoke-WebRequest -SkipHttpErrorCheck -Method Post `
  -Uri "$url/rest/v1/user_progress" -Headers $h -ContentType 'application/json' `
  -Body (@{ user_id = $A_ID; kanji_id = 1; rating = "known" } | ConvertTo-Json) |
  Select-Object StatusCode, Content
```

Ожидаемый результат: `[]` для чтения (это **нормальное** поведение RLS —
строки молча отфильтрованы, а не отдана ошибка) и `403` с текстом
`new row violates row-level security policy for table "user_progress"` для записи.

Для сравнения сделайте то же с токеном A — вернутся его 3 строки.

## 9. Шаг 9. Офлайн-кэш при смене аккаунта в одном профиле

Дополнительная проверка на утечку через `localStorage`: кэш и очередь
несохранённых отметок хранятся с ключами, включающими `userId`
(`kanji-n5-cache-<uuid>`, `kanji-n5-pending-<uuid>`), поэтому при смене
пользователя в одном окне данные не должны «переехать».

1. В окне A нажмите «Выйти» (появится форма входа).
2. Войдите как **B** в том же окне.
3. [ ] сводка соответствует B, а не A;
4. [ ] DevTools → Application → Local Storage: два разных ключа
   `kanji-n5-cache-<uuidA>` и `kanji-n5-cache-<uuidB>` со своим содержимым.

## 10. Как читать результаты: симптом → диагноз

| Что увидели | Что это значит |
|---|---|
| B видит строки A в ответе на `select` | сломана/отсутствует `SELECT`-политика (`auth.uid() = user_id`) |
| Вставка B с `user_id` A прошла (нет ошибки) | **критично**: нет `WITH CHECK` в `INSERT`-политике |
| `UPDATE`/`DELETE` B по строкам A вернул строки | нет `USING` в `UPDATE`/`DELETE`-политике |
| B видит email A в `users` | сломана политика на `public.users` |
| Ошибка `permission denied for table` у гостя | это **правильно**: `GRANT` выдан только роли `authenticated` |
| Пустой массив `[]` вместо ошибки | это **правильно**: RLS фильтрует строки молча |
| Ошибка `42501 new row violates row-level security policy` | это **правильно**: `WITH CHECK` не пропустил чужой `user_id` |
| `permission denied for table kanji` при входе | потеряны `GRANT` из `supabase_seed_kanji.sql` (не про RLS) |

Если что-то из первой половины таблицы воспроизвелось — проверьте в SQL Editor,
что RLS включён и политики на месте:

```sql
select relname, relrowsecurity
from pg_class
where relname in ('users', 'user_progress', 'kanji');

select tablename, policyname, cmd, qual, with_check
from pg_policies
where schemaname = 'public'
order by tablename, cmd;
```

Ожидаемо: `relrowsecurity = true` для `users` и `user_progress`; у `user_progress`
четыре политики (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), у `users` — три.

## 11. Особенности именно этого проекта

- **`kanji` намеренно открыта гостям** (`grant select ... to anon` + политика
  «Anyone can read kanji»). Это общий справочник, а не пользовательские данные,
  поэтому чтение без входа — не утечка.
- **У `users` нет `DELETE`-гранта.** Удалить профиль через API нельзя; строки
  удаляются каскадом при удалении пользователя в `auth.users`.
- **`ensureProfile`** делает upsert с `id` текущего пользователя. Если подменить
  `id` на чужой, сработает `WITH CHECK` — вставка упадёт.
- **`is_anonymous`** ставится триггером из `raw_user_meta_data`; для обычной
  регистрации всегда `false`.
- **Service role key обходит RLS.** В `.env` его нет — и это правильно для
  фронтенда. Никогда не добавляйте `service_role` в клиентское приложение:
  любой посетитель получит полный доступ ко всем данным.

## 12. Уборка после теста

1. Удалите тестовые строки прогресса (Table Editor → `user_progress` → фильтр по
   `user_id` тестовых аккаунтов).
2. Authentication → Users → удалите `kanji-test-a@` и `kanji-test-b@`
   (профили в `public.users` удалятся каскадом).
3. Уберите `RLS_USER_*` из `.env`.
